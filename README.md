# ЛР №4-5. Реалізація симетричного шифрування з використанням AES

Консольний застосунок для шифрування файлів у режимах **AES-CBC + HMAC-SHA256** (Encrypt-then-MAC) і **AES-GCM** (AEAD).
Ключі виводяться з пароля через PBKDF2. Є журналювання у форматі JSON, вимірювання швидкодії та імітація підміни файлів.
Проєкт побудовано на демо-пакеті викладача; виправлення шаблону перелічено в кінці цього файлу.

Результати вимірювань швидкодії: [`outputs/bench.md`](outputs/bench.md).

## Вимоги та встановлення

- Python 3.10+ (перевірено на Ubuntu Server 24.04, Python 3.12)
- бібліотека `cryptography` (див. `requirements.txt`)

```bash
git clone <URL цього репозиторію> lab4-5 && cd lab4-5
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

## Швидкий старт

Пароль запитується інтерактивно (не потрапляє в історію команд). Мінімальна довжина пароля 12 символів.

```bash
python aes_cli.py params                                   # параметри шифрування
python aes_cli.py key new --label default                  # створити ключ
python aes_cli.py enc --in data/sample.txt --out outputs/sample.enc --mode gcm --label default
python aes_cli.py dec --in outputs/sample.enc --out outputs/sample.dec --label default   # режим береться із заголовка
python aes_cli.py shell                                    # REPL: зміна режиму без перезапуску
python benchmark.py --modes cbc gcm --sizes 1MB 10MB 100MB --repeat 3
python tamper_demo.py --file outputs/sample.enc --target tag    # навмисне псування
python analyze_logs.py                                     # аналіз журналу
python -m unittest -v tests/test_roundtrip.py              # тести
```

## Формат контейнера

```
CBC: MAGIC "ALAB"(4) | HDRLEN(2) | HEADER(JSON) | IV(16) | CIPHERTEXT | HMAC-SHA256(32)
GCM: MAGIC "ALAB"(4) | HDRLEN(2) | HEADER(JSON) | CIPHERTEXT | TAG(16)
```

Заголовок містить версію формату, режим, алгоритм, IV або nonce і `key_id`. У CBC HMAC обчислюється над `header || IV || ciphertext`. У GCM заголовок передається як AAD (разом з AAD користувача, якщо задано `--aad`). Отже, будь-яка зміна заголовка, IV/nonce, шифртексту або тегу виявляється.

## Ключі: ініціалізація та життєвий цикл

**Процедура ініціалізації** (`key new --label L [--bits 128|192|256]`):
1. Перевіряються вимоги: унікальна мітка, пароль щонайменше 12 символів, допустима довжина ключа (128/192/256 біт), не менше 200 000 ітерацій.
2. Генерується випадковий salt, 16 байт (`os.urandom`).
3. PBKDF2-HMAC-SHA256 (310 000 ітерацій) виводить `довжина_ключа + 32` байти: перша частина є ключем AES, решта 32 байти є окремим ключем HMAC.
4. Перевіряється довжина виведеного ключа.
5. Обчислюється `key_id = SHA-256(enc_key)[:16]`. Якщо такий `key_id` уже є, створення забороняється.
6. У `keystore.json` (права 600) записуються лише метадані: мітка, key_id, довжина, salt, ітерації, KDF, дати, лічильник використань, статус. **Самі ключі на диск не записуються**: вони щоразу виводяться з пароля.

**Правила життєвого циклу:**

| Стан | Умова | Шифрування | Розшифрування |
|---|---|---|---|
| active | нормальний стан | так | так |
| exhausted | виконано `max_uses` (1000) шифрувань | ні | так |
| expired | минуло `MAX_AGE_DAYS` (90) днів | ні | так |
| revoked | `key revoke --label L` | ні | так (із записом WARNING у журналі) |

- Неактивний ключ не можна використати для нових шифрувань. Ротація: створюється новий ключ із новою міткою (`key new`), старий відкликається (`key revoke`). Старі файли розшифровуються старим ключем, бо `key_id` записано в заголовку файлу.
- Обмеження кількості використань також обмежує кількість випадкових nonce GCM на один ключ: NIST SP 800-38D допускає не більше 2^32 повідомлень з випадковим 96-бітним nonce.
- Неправильний пароль виявляється до розшифрування: виведений ключ не дає збережений `key_id`.
- IV (CBC) і nonce (GCM) генеруються випадково (`os.urandom`) для кожного файлу. Повтор випадкового значення не виключений повністю, але для 96-бітного nonce за 1000 шифрувань одним ключем його ймовірність нехтовно мала.

## Параметри шифрування

Параметри задаються в `config.py`, перевіряються під час запуску (`validate_config`) і виводяться командою `params` (або `params` у REPL):

| Параметр | CBC-HMAC | GCM |
|---|---|---|
| Розмір блоку | 128 біт (фіксований стандартом AES) | 128 біт |
| Довжина ключа | 128/192/256 біт (`key new --bits`) | 128/192/256 біт |
| IV / nonce | 16 байт, випадковий | 12 байт, випадковий |
| Паддинг | PKCS#7 | не потрібен (потоковий режим) |
| Цілісність | HMAC-SHA256, 32 байти | тег GCM, 16 байт |

**Розширюваність:** режими зібрано в словнику `MODES` у `crypto_aes.py`. Щоб додати новий режим (наприклад, CTR+HMAC), достатньо написати пару функцій `encrypt_x/decrypt_x` з тією самою сигнатурою і додати запис у `MODES`; CLI та REPL підхоплять його автоматично.

## Журналювання та аналіз логів

Журнал `logs/aes.jsonl` має формат JSON Lines, час записується в UTC. Ключі, паролі та IV/nonce не логуються.

| Подія | Рівень | Значення |
|---|---|---|
| `enc_start` / `enc_ok` | INFO | шифрування: файл, розмір, режим, час, key_id, лічильник використань |
| `dec_start` / `dec_ok` | INFO | розшифрування успішне, `tag_valid: true` |
| `dec_integrity_fail` | ERROR | не пройдено перевірку HMAC/тегу (`tag_valid: false`) |
| `dec_error`, `enc_error` | ERROR | неправильний пароль, чужий ключ, пошкоджений заголовок, політика ключа |
| `dec_with_revoked_key` | WARNING | розшифрування відкликаним ключем |
| `key_new`, `key_revoke`, `key_error` | INFO/WARNING/ERROR | керування ключами |
| `repl_start`, `mode_change`, `repl_stop` | INFO | робота в REPL |

**Як аналізувати:**

```bash
python analyze_logs.py                         # статистика, знахідки і тривоги
grep '"level": "ERROR"' logs/aes.jsonl         # усі помилки
grep dec_integrity_fail logs/aes.jsonl         # спроби підміни
grep WrongPasswordError logs/aes.jsonl         # неправильні паролі
```

**Що вважати інцидентом:**

| Ознака | Пріоритет | Дія |
|---|---|---|
| `dec_integrity_fail` | високий | файл змінено або пошкоджено: не використовувати, відновити з резервної копії, з'ясувати джерело |
| 3 і більше помилок для одного файлу або ключа (`ALERT` в `analyze_logs.py`) | високий | можливий підбір пароля або серія атак: перевірити, хто запускав, змінити пароль або ключ |
| `WrongPasswordError` | середній | одинична помилка користувача або спроба підбору |
| `dec_with_revoked_key` | середній | відкликаний ключ ще використовується: перешифрувати дані новим ключем |
| порушення політики ключа | низький | нагадати правила, створити новий ключ |

Як це посилює безпеку: журнал показує, які файли змінювалися, хто і коли підбирав пароль, де ще використовуються відкликані ключі. Ці дані є підставою для ротації ключів, блокування облікових записів і перевірки резервних копій. У реальній системі журнал слід передавати до централізованого сховища (SIEM) і захистити від змін.

## Результати імітації підміни

| Режим | Що змінено (1 біт) | Результат розшифрування |
|---|---|---|
| GCM | шифртекст | `IntegrityError: GCM InvalidTag`, вихідний файл не створено |
| GCM | тег | `IntegrityError: GCM InvalidTag` |
| GCM | інший AAD (`--aad`) | `IntegrityError: GCM InvalidTag` |
| CBC-HMAC | шифртекст | `IntegrityError: HMAC verification failed`, вихідний файл не створено |
| CBC-HMAC | IV | `IntegrityError: HMAC verification failed` |
| CBC-HMAC | тег (HMAC) | `IntegrityError: HMAC verification failed` |

Перевірку виконують також автоматичні тести (`tests/test_roundtrip.py`, тест `test_tamper_detected`).

## Зміни відносно демо-пакета

1. **Розшифрування CBC не працювало.** IV записується після заголовка, але під час розшифрування він не зчитувався окремо і потрапляв у шифртекст, тому HMAC ніколи не збігався. Тепер IV зчитується окремо, а HMAC обчислюється над сирими байтами заголовка.
2. Без каталогу `logs/` програма падала (`FileNotFoundError`): каталог тепер створюється автоматично.
3. Помилка GCM `InvalidTag` мала порожній текст і в журналі не було видно причини. Тепер помилки цілісності мають окремий тип `IntegrityError` і зрозуміле повідомлення.
4. Перевірка повторного використання ключа порівнювала `key_id`, який через випадковий salt завжди новий. Додано заборону повторної мітки, ліміт використань, строк дії і відкликання (`key revoke`), як радить методичка.
5. `benchmark.py` лише виводив підказку; тепер він виконує вимірювання (середнє з повторів, MB/s, CPU, пам'ять).
6. `tamper_demo.py` міг змінити байт у MAGIC або довжині заголовка. Тепер ділянка вибирається явно (`--target ciphertext|tag|iv|header`).
7. REPL не вів журнал і не рахував використання ключа: тепер CLI і REPL використовують спільні функції.
8. У GCM заголовок не автентифікувався: тепер він передається як AAD.

## Попередження безпеки

- Демо-код не призначений для промислового використання без аудиту.
- Розшифрування читає весь файл у пам'ять (пікове споживання приблизно в 3-4 рази більше за розмір файлу, див. `outputs/bench.md`). Для великих файлів потрібна потокова обробка з тимчасовим файлом.
- Стійкість ключа обмежена стійкістю пароля.
